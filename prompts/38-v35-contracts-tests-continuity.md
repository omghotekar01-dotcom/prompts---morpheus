# MASTER PROMPT #38 — CONTRACT/API/SCHEMA CATALOG, TEST ENCYCLOPEDIA & CONTINUITY SYSTEM

## Mission
Make MORPHEUS maintainable across long development cycles by defining the contracts, tests and decision records that prevent semantic drift. This volume is the continuity layer between research intent, implementation, CI, release evidence and future AI/engineer contributors.

# 1. Contract hierarchy
The highest-authority executable contracts are versioned schemas, typed models, capability registries and tests. Prose explains them but does not silently override them.

Maintain explicit contracts for:
- MWS raw input;
- resolved MWS/assumption ledger;
- WorkloadIR;
- PrimitiveManifest/implementation identity;
- MachineProfile;
- CalibrationProfile/Measurement;
- CostEstimate;
- ConfigurationIR;
- SearchSummary/Pareto result;
- generated ArtifactManifest;
- compile/correctness VerificationManifest;
- benchmark ExperimentManifest;
- ObservedWorkloadSnapshot;
- AdaptationDecision/MigrationPlan;
- FeatureRegistry/promotion policy;
- evidence ledger/release manifest/reproducibility manifest.

# 2. Versioning rules
Every contract has a stable schema/protocol/version identifier. Breaking semantic changes require a version increment plus migration/compatibility documentation. Backward-compatible optional fields must have explicit defaults and cannot alter old semantic hashes unless intended by the version policy.

Never reuse a schema version for incompatible semantics.

# 3. MWS catalog
MWS must define dataset name/version, record count/scale semantics, typed fields, cardinality/selectivity metadata, logical queries/mutations, operation weights/rates, access distributions, constraints, objective and optional temporal modes.

Validation classes:
- syntax/schema error;
- semantic contradiction;
- unsupported capability;
- ambiguous value requiring assumption/review;
- valid resolved specification.

# 4. WorkloadIR catalog
WorkloadIR is deterministic compiler input. It should contain stable field IDs, normalized operation weights, typed distributions, resolved defaults and source-spec identity. It contains logical intent, not selected physical primitives or measurements.

# 5. Primitive/implementation catalog
Distinguish primitive family from physical implementation ID. Capabilities, parameter schema, maturity/search eligibility and update/concurrency semantics are versioned. Calibration evidence binds to implementation identity, not a vague family name.

# 6. Calibration/evidence catalog
Measurement keys include at least primitive, operation, implementation ID, scale and typed access distribution when applicable. Store repetition/dispersion/protocol/machine metadata. Exact-match lookup must fail closed on distribution, scale or implementation mismatch rather than pretending evidence transfers automatically.

# 7. ConfigurationIR catalog
ConfigurationIR records selected physical nodes, parameters, logical routes, ownership/update dependencies, objective/constraints and evidence/model provenance. Its canonical hash identifies the physical design decision independent of generated source formatting.

# 8. Artifact contracts
Artifact manifests bind generated bytes/source to WorkloadIR/ConfigurationIR, generator version, toolchain target and verification state. States are monotonic only when new evidence is added; a source file does not self-certify compilation/correctness/performance.

# 9. API contract
Maintain v1 compatibility surfaces where intentionally supported and evidence-safe v2 endpoints for advanced controls. The OpenAPI route contract fingerprint should cover path, HTTP method, operation ID, request-required flag and response-code set. A route fingerprint detects structural API change, not every JSON-field semantic change.

Critical endpoint categories:
- health/readiness;
- synthesis/workload IR;
- runs/artifacts/evidence;
- calibration import/activation/coverage;
- research evaluation;
- capabilities/completion;
- feature policy/evaluation;
- runtime sessions/migrations/data-plane;
- release/evidence controls where exposed.

# 10. CLI contract
The CLI must offer a non-UI proof path for validation, synthesis, generation, verification and evidence export where implemented. Commands use deterministic exit codes and machine-readable output modes. CLI behavior must use the same core schemas/engine as the API rather than a parallel logic fork.

# 11. Event catalog
For long-running jobs/adaptation, define structured events such as:
- JOB_ACCEPTED/STARTED/COMPLETED/FAILED/CANCELLED;
- SPEC_VALIDATED;
- IR_LOWERED;
- SEARCH_STARTED/CANDIDATE_EVALUATED/SEARCH_COMPLETED;
- ARTIFACT_GENERATED/COMPILED/VERIFIED;
- BENCHMARK_STARTED/MEASUREMENT_RECORDED;
- DRIFT_DETECTED;
- MIGRATION_STAGED/COMMITTED/ROLLED_BACK/ABORTED;
- CLAIM_GATE_ALLOWED/BLOCKED.

Events carry immutable IDs, timestamp, run/session identity and provenance references. Avoid storing giant payloads directly in event logs.

# 12. Error contract
Errors should be typed enough for users/tests to distinguish invalid input, unsupported semantics, infeasible constraints, missing evidence, worker/toolchain failure, verification failure and internal fault. Never turn a correctness failure into an empty successful result.

# 13. Test pyramid
Maintain meaningful tests across:
1. pure unit/property tests;
2. schema/golden tests;
3. primitive differential/state-machine tests;
4. synthesis/search tests;
5. generated artifact compile/differential tests;
6. API/CLI contract tests;
7. persistence/evidence integrity tests;
8. runtime migration/concurrency tests;
9. release/reproducibility tests;
10. cross-platform CI and sanitizer profiles.

Test count is not a quality metric by itself. Optimize for semantic coverage and failure detection.

# 14. Specification tests
Include valid and invalid MWS fixtures for every field/query/distribution/constraint type. Test duplicate names, unknown references, zero/negative values, non-finite numbers, contradictory parameters and canonical equivalence.

# 15. Primitive test encyclopedia
For each primitive test:
- empty state;
- one item;
- duplicate/upsert semantics;
- missing lookup/delete;
- min/max/boundary keys;
- randomized operation sequences;
- large enough cases to exercise split/grow/rebalance/container transitions;
- memory ownership/lifetime;
- copy/move policy if supported.

# 16. Search tests
Test deterministic tie-breaking, candidate counts, truncation flags, hard-constraint rejection, exhaustive tiny spaces, greedy/beam behavior, Pareto dominance, canonical candidate IDs and unsupported operation handling.

# 17. Cost/calibration tests
Test exact measurement selection, distribution mismatch, scale mismatch, stale implementation, missing evidence, mixed calibrated/bootstrap provenance, uncertainty propagation and no accidental operation aliasing.

# 18. Codegen tests
Golden source fragments are secondary to executable behavior. Test clean compilation on supported toolchains, schema-derived operations, stateful differential correctness and deterministic artifact identity where intended.

# 19. Runtime/adaptation tests
Test drift threshold boundaries, hysteresis/cooldown, exact generation preconditions, migration verification, health failure, compensation, duplicate calls, wrong-session calls, rollback and concurrent reader validity for implemented data-plane mechanisms.

# 20. Security tests
Include parser/path/command/resource abuse, feature-policy fail-closed behavior, evidence tampering, malicious metadata and AI/prompt-injection trust-boundary cases. Security tests do not replace independent security review.

# 21. Research tests
Research tooling tests validate methodology contracts: frozen seeds, no leakage, grouped held-out evaluation, paired statistics, confidence-interval reproducibility, baseline identity and preservation of negative outcomes.

# 22. Release tests
Claim gates must use roles of artifacts physically present, not self-declared evidence-role names. Structural validators and cross-artifact hash links fail closed. Reproducibility manifests bind exact commit and relevant API/feature-policy identities.

# 23. CI matrix
Regular CI should cover declared Python versions, Linux/Windows native builds, sanitizers and frontend production build. Measurement smokes verify protocol/execution but are not publication-grade benchmark evidence. Add optional macOS/ARM only after support is real.

# 24. Test encyclopedia target
Aim toward hundreds/thousands of meaningful generated/property cases over time, but organize them by invariant rather than padding test count. Maintain a matrix mapping contracts/invariants to tests and CI jobs.

# 25. ADR system
Record Architecture Decision Records for high-impact decisions:
- chosen MWS/IR version semantics;
- primitive implementation replacement;
- calibration identity policy;
- search strategy changes;
- runtime publication model;
- sandbox/security tier;
- ABI changes;
- evidence/release protocol changes.

Each ADR states context, decision, alternatives, consequences, evidence and supersession status.

# 26. Evidence ledger
Maintain a machine-readable capability/completion ledger that says IMPLEMENTED/TESTED/MEASURED/RESEARCH/BLOCKED with scope encoded in the value. Completion percentages count explicit engineering gates only and list excluded external outcomes.

# 27. Continuity checkpoint
At every meaningful phase record:
- exact Git head;
- what changed;
- tests/CI run IDs and conclusions;
- new schema/protocol versions;
- known limitations;
- next dependency-ready work.

Do not rely on conversational memory as the sole project record.

# 28. Implementation map
Maintain clear repository mapping among backend/core/frontend/benchmark/research/release/docs/prompts. One canonical file per concept where possible. Avoid duplicated `final-final-v2` documents.

# 29. AI contributor protocol
An AI agent must read current repository/test state before changing code. It may not infer completion from prompt text. It should make coherent commits, run focused and integration tests, preserve truth boundaries and avoid large generated/binary artifacts in Git.

# 30. Deprecation policy
Deprecated routes/schemas/features remain explicitly marked for a transition period when compatibility matters. Define replacement and removal version/date policy. Never silently reinterpret old persisted evidence under new semantics.

# 31. Documentation-as-contract tests
Where practical, validate example specs, command snippets, schema names, prompt corpus completeness and critical links in CI. Documentation that describes unsupported behavior must be corrected or clearly labeled future/research.

# 32. Definition of done
This continuity layer is complete when a fresh engineer/AI can determine, from repository files alone:
- what MORPHEUS currently supports;
- which contracts are normative;
- how to run/verify it;
- why major decisions were made;
- what evidence supports each capability;
- what remains research/future;
- whether the exact current head is green.

## Truth boundary
Contracts/tests/ADRs/provenance dramatically reduce project drift, but they do not prove the absence of defects or guarantee future compatibility. Claims remain bounded by executed tests and evidence on the exact revision.
